## What This Skill Is

The S-FOUNDATION-SUITES Skill is the **Teal Claude relay** for Foundation Suites engagement. Where `FOUNDATION-SUITES-GUIDE.md` is the canonical Reference Design (13-cycle empirical proof + N-agent generalization), this Skill is the **operational surface** Teal Claude loads when:

- User invokes the Foundation Suites menu via `/cascade` or `/cascade:magic-shotgun`
- Conductor classifies user scope as Foundation-Grounding-needed (any cascade Length ≥3)
- A sub-Diamond Foundation Triplet/Quartet needs to be dispatched
- A new Tier-0 Foundation-Only → Diamond planning surface is required (4-Tier Magic Shotgun)

## NEW · Foundation-Only Tier (Tier-0 of 4-Tier Magic Shotgun)

**Per user directive at Cycle 113**: a Foundation-Only Tier is added to Magic Shotgun where Foundation Suites compose into a **Diamond planning surface** rather than immediately dispatching Cobalt. The user reviews the Diamond plan, then chooses whether to engage Tier-1 (Traditional 2-Stage with R5) or Tier-2 (3-Stage Per-Isolation).

### Tier-0 · Foundation-Only → Diamond Pattern Definition

```
Stage 1 · Foundation Magic Shotgun (parallel · Triplet / Quartet / 5-Suite):
  R1 Red       ─┐
  R2 Orange    ─┤
  R4 Green     ─┼─→ N parallel Foundation reports
  R6 Purple    ─┤
  R7 Fuchsia   ─┘
                ↓
       Main Thread Synthesis → Diamond Plan (Macro WGB OR sub-Diamond WGB)
                ↓
       [USER REVIEW · Conference]
                ↓
   ┌────────────────────────────────────┐
   │  User decides next engagement:     │
   │  • Tier-1 Traditional 2-Stage      │
   │  • Tier-2 3-Stage Per-Isolation    │
   │  • Tier-0 close (plan-only · halt) │
   └────────────────────────────────────┘
                ↓
       [Per user selection · dispatch R5 or escalate or close]
```

### When to Use Tier-0 (Foundation-Only)

- **User wants to review Diamond plan BEFORE actualization** · staged engagement
- **Macro Open** where sub-Diamond structure must lock before any Cobalt dispatch
- **Scope uncertain** at Foundation time · plan-only output verifies user intent
- **Diamond-of-Isolations planning** where multi-Gap isolation count is unknown · Foundation surfaces it · user decides isolation count
- **Refinement Macros** where prior Macro substrate must be inspected before refinement scope locks

### Tier-0 vs Other Tiers

| Tier | Dispatch | Cobalt Engagement | Use Case |
|---|---|---|---|
| **Tier-0 NEW** | Foundation Suites only | Deferred (plan-only) | User review of Diamond before R5 dispatch |
| **Tier-1** | Foundation → R5 Cobalt | Immediate | Standard sub-Diamond · 1 Diameter Gap |
| **Tier-2** | Foundation → N R3 → N R5 | Per-isolation | Refinement Macros · multi-Gap isolation |
| **Tier-3** | Foundation → Diamond → N R3 → N R5 | Per-isolation after Diamond | (future · speculative · combines Tier-0 + Tier-2) |

### Tier-0 Engagement Sequence

```
Step 1: Conductor receives Macro-class or sub-Diamond-class scope
Step 2: User selects Tier-0 (Foundation-Only) via menu
Step 3: Conductor composes Foundation Magic Shotgun (3-7 Round selection per complexity)
Step 4: Dispatch Foundation Suites (Tier-1 parallel · single message)
Step 5: All N Foundation Suites return · Conductor synthesizes
Step 6: Conductor writes Diamond Plan / Macro WGB
Step 7: Conference: present Diamond Plan to user · ask for next engagement
Step 8a: User selects Tier-1 → dispatch R5 Cobalt (Traditional 2-Stage close)
Step 8b: User selects Tier-2 → dispatch N R3 Yellow per-isolation (3-Stage continuation)
Step 8c: User selects close → Tier-0 plan-only · awaits future session continuation
```

### Use Case Examples

1. **Macro Open with unclear sub-Diamond count** → Tier-0 Foundation Magic Shotgun → R6 determines sub-Diamond count → user reviews Cerulean Task Chain → decides to engage Tier-1 per sub-Diamond
2. **Refinement Macro with unclear isolation count** → Tier-0 5-Suite Macro Open → Foundation surfaces N Diameter Gaps → user reviews Diamond-of-Isolations → engages Tier-2 (3-Stage)
3. **Staged engagement preference** → user wants to inspect Foundation reports before any implementation Lambda-event · Tier-0 produces verifiable disk artifacts without committing to R5 dispatch

## Foundation Suite Dispatch Pattern (Disjoint Scope Discipline)

Per `FOUNDATION-SUITES-GUIDE.md` §2, every Foundation Magic Shotgun dispatch MUST include in each agent prompt:

> *"Suites X/Y/Z are running concurrently with disjoint scopes. R{1|2} {curates|names}; R3 designs structure; R6 sequences execution. Do not duplicate the other Suite's scope."*

### Scope Discipline Per Suite

| Suite | Scope | Output File |
|---|---|---|
| **R1 Red** | Inventory · existing patterns · dependencies | `SUITE-1-RED-{sub}-CURATION.md` |
| **R2 Orange** | Verbose pattern names · Diameter framing | `SUITE-2-ORANGE-{sub}-PROSPECTING.md` |
| **R3 Yellow** | Type shapes · file structures · Wave inventory | `SUITE-3-YELLOW-{sub}-ARCHITECTURE.md` |
| **R4 Green** | Bidirectional examination · edge cases · REFINE verdict | `SUITE-4-GREEN-{sub}-BIDIRECTIONAL.md` |
| **R6 Purple** | Wave-by-Wave execution order · M10 Mid-Flight-Calibrator | `SUITE-6-PURPLE-{sub}-ORCHESTRATION.md` |
| **R7 Fuchsia** | Foundation-level clinical retrospective (Macro opens only) | `SUITE-7-FUCHSIA-{sub}-FOUNDATION-CLINICAL.md` |

Each agent does NOT propose work in the other agents' scopes. R2 doesn't sketch architecture; R3 doesn't name patterns; R6 doesn't redesign types.

## R3 vs R6 Reconciliation Discipline

R3 (Architect) and R6 (Orchestrator) sometimes disagree at the substrate level. The main thread's synthesis decision resolves disagreements — the decision IS documented in the sub-Diamond's WGB. **Erasure** (picking one and ignoring the other without record) is an anti-pattern.

### Reconciliation Documentation Rule

Every R3 vs R6 disagreement resolved by main thread MUST produce:

1. Each suite's position stated explicitly
2. The synthesis decision stated explicitly
3. The method-level lesson extracted as a Maintain or Gainy entry in Onyx

Source: `FOUNDATION-SUITES-GUIDE.md` §4 · 4 reconciliations documented in Macro 1.

## Foundation Suite Output as Substrate

Foundation Suite output files (`SUITE-*-{sub}-*.md`) remain in `Cascades/Working/` as substrate for the NEXT sub-Diamond. They are local Lambda evidence · NOT committed deliverables.

This is the **Suite-Output-as-Substrate Pattern** (`FOUNDATION-SUITES-GUIDE.md` §7).

When MCSP (Mid-Cycle Scope Pivot) fires and the current sub-Diamond ships less than the Foundation Suites designed, the Foundation Suite files **remain as substrate** for the next sub-Diamond's grounding. Foundation Suites are expensive (~6 minutes wall-clock + ~3 Tier-1 agent context costs); re-running them for the same scope is wasteful.

## Diameter to Triadic Thinking Band

The Triadic Thinking Band (`.claude/CLAUDE.md` §Section 4 skeleton 2-4-6→5) runs PRIVATELY in-context:

- **S2 Name → S4 Examine → S6 Orchestrate → S5 Plan**

Foundation Suites at-once runs PUBLICLY as Tier-1 dispatches with verifiable disk artifacts:

- **R2 Name + R4 Examine + R6 Sequence + R5 Build (Cobalt)**

The Foundation Suites pattern IS the Lambda-event instantiation of the Triadic Thinking Band — same compositional pattern, different tier (private cognitive vs public Lambda-event).

## Self-Check (Foundation Suites Contract)

Before issuing the Foundation Magic Shotgun, the Conductor verifies:

1. **Round count matches complexity** per `FOUNDATION-SUITES-GUIDE.md` decision criteria
2. **R6 Purple included** when ≥3 Rounds fire (M10 Mid-Flight-Calibrator role)
3. **R4 Green included** for M19 Interactive-class moments (M31 mandatory)
4. **R7 Fuchsia at Foundation level** ONLY for Macro opens or Refinement Macros (NOT standard sub-Diamond Foundation Triplets)
5. **Disjoint scope coordination note** present in each agent prompt
6. **Output file paths** are unique per Suite · prevent collision
7. **Tier selection** (0/1/2) confirmed with user when ambiguous

If any check fails → re-plan. This is the **Foundation Suites Contract**.
