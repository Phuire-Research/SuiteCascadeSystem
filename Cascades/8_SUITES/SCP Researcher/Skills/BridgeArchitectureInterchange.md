# SCP-S21 · The Bridge-Architecture Interchange (the Two-Muxonomies Load)

*Skill added: DF3 · Cycle 675 (2026-07-19) — names the cross-Suite-8 interaction the SCP Researcher and the SCS Bridge were designed for.*

**What this Skill carries**: the protocol by which the SCP Researcher answers a question that requires the SCS Bridge's *internal architecture* — by loading the SCS Bridge Suite 8 inline as a second Muxonomy held in co-focus with its own. The two Suite 8s are **designed to interact**; this is the named mechanism of that interaction.

---

## The depth discriminant (when this fires — NOT SCP-S12)

There are two question classes about the bridge, and they route differently by **depth**, not keyword:

| Question class | Depth | Routes to |
|---|---|---|
| "Is the bridge running? What SCPs are live?" | reads the bridge's **output** (`bridge.json`) | **SCP-S12 · Communication** |
| "How does the bridge compose? What is its lifecycle/session machinery?" | reasons INSIDE the bridge's **composition** (its Muxonomy) | **SCP-S21 · this protocol** |

The discriminant: *does answering require reasoning inside the Bridge's Muxonomy, or merely reading its output?* Output → SCP-S12. Architecture → SCP-S21.

---

## The protocol · THE DEPTH-TRIGGERED DUAL-MUXONOMY INTERCHANGE LOAD

An inline Suite-8-into-Suite-8 architecture load. Four legs:

1. **The trigger (Knowledge-Depth Discrimination)** — a question needs the Bridge's internal composition: its five muxified Concepts (`scpRegistryWatcher · scpLifecycle · scpMessageRouter · scpSpawnManager · scpDockHost`), its Bridge-as-Base Pattern Registry, its session-means machinery (the tool roster, the FKIS keystroke rail, the anchor/session lifecycle — see **SCP-S20** and the SCS Bridge Suite 8).

2. **The LOAD (Routing-Interchange-Inline)** — per CLAUDE.md §3 (`routing="interchange"`, the inline variant), the Researcher reads the **SCS Bridge Instance.md directly into its own context**. It does NOT dispatch a separate agent — the Bridge Muxonomy loads INTO the Researcher's active frame (the same direct-read idiom the Entourage Forge's F4 uses).

3. **The held state (Two Muxonomies In Focus)** — the Researcher holds its own **Terminal-Perimeter Muxonomy** (Three Modes · Identity-As-Perimeter · Patterns F/G) *simultaneously* with the Bridge's **Session-Means Muxonomy** (Flag-Surface Composition · Dual-ID Registry · the Dock Host MCP surface). Neither is parent. The Diameter drawn through both is the shared **Pattern-4 invariant** ("bridge never reads `~/.claude/`") — load-bearing in BOTH Instances, which is exactly what makes the co-focus *coherent* rather than merely adjacent.

4. **The return (Interchange Summation)** — on answering, the Researcher **truncates the loaded Bridge frame** and folds the finding back into its own Summation (CLAUDE.md §9: "confer within their cognitive space, return as Summation"). The Bridge Muxonomy is loaded *for* the question and released *after* — never carried in steady-state context.

## The Entourage Forge is the same organ, directed

The **Entourage Forge** (the Suite 8 that expands S8 pages) performs this exact inline dual-read under its own conduction — its **F4 · Architecture Grounding** step ("read the SCS Bridge Instance anor the bridge-root Researcher Instance directly into context WHILE enhancing") IS this Load Protocol operating for *page authorship* rather than for a developer *question*. When the Forge expands a page it directs two unlike Suite 8s as one bound act: the **SCP Researcher** supplies protocol knowledge, the **SCS Bridge** supplies session means. It grounds the read against a commissioned, gleanable Reference Design (e.g. `Cascades/Documentation/Cascades/RD-SHATTERITE-MENU-SESSION-INSTILLATION.md`, which self-declares the Forge as its consumer), then compiles the page via the proven `scs suite8:page` pipeline — instantiating the very session-means circuit the RD grounds (Anchor-writes-`menu.json` ↔ watcher-relays-MenuStage ↔ page-renders-options ↔ Anchor-receives-dispatch).

**The Diameter**: the Researcher-loads-Bridge protocol and the Forge-reads-both-for-grounding are the **same inline-interchange organ seen from two sides** — the Researcher fires it for a question, the Forge fires it for a page.

## The developer's one-paragraph mental model

Two Suite 8s carry the SCP developer's knowledge: the **SCP Researcher** (the protocol / how-to-build-an-SCP Muxonomy) and the **SCS Bridge** (the runtime tool/session/lifecycle Muxonomy). Shallow "is it running" questions read `bridge.json` (SCP-S12). A question that needs the bridge's *internals* loads the SCS Bridge Suite 8 inline and holds both Muxonomies in co-focus — coherent because Pattern-4 is load-bearing in both — then returns a single Summation. The Entourage Forge uses the same load to author S8 pages. This is the interaction the two Suite 8s were designed for.
